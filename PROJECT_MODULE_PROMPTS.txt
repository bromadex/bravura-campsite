MODULE VISION
═══════════════════════════════════════════════════════════════════════════════

Think Trello boards + Slack channels + cost tracking, built into the ERP.

Every project is a workspace. Inside it:
  - A KANBAN BOARD of tasks (drag cards between columns)
  - A DOCUMENT HUB (upload files, photos, drawings, permits)
  - An ACTIVITY FEED (comments, status changes, mentions — Slack-style)
  - A TEAM roster with roles
  - COST TRACKING that auto-aggregates from fuel, fleet, equipment, inventory,
    contractors, and manual entries
  - MILESTONES & PHASES with progress bars
  - LABELS / TAGS for categorization (like Trello labels)

Cross-module: projects don't duplicate data. A fuel issuance, equipment log,
inventory issue, or contractor timesheet gets tagged with a project_id, and
costs flow in automatically.

Module code: PJ
Permission pattern: projects.view / projects.create / projects.edit /
                    projects.delete / projects.approve
T-code range: PJ01–PJ20
Migration range: 0085–0094 (general range)

2. Cross-module project tagging:
   - Adding project_id to existing tables is NULLABLE (optional tagging)
   - Other module forms get a "Project" dropdown showing active projects
   - The dropdown only shows if projects.view permission is granted
   - If no project selected, transaction works as before (no project link)
   - This is backward-compatible — no existing functionality breaks

3. Project codes:
   - Auto-generated per site: PJ-001, PJ-002, etc.
   - Counter stored in module_settings table (like BRA-xxx for employees)
   - Display format: {site_prefix}-PJ-{number}

4. Supabase Storage setup:
   - Bucket: "project-documents" (public: false)
   - RLS policy: user must have projects.view for the project's site_id
   - Upload limit: 50MB per file
   - Folder structure: {site_id}/{project_id}/{folder_name}/{filename}

5. Board drag-and-drop:
   - Use HTML5 Drag and Drop API (no external library needed)
   - On drop: update task.column_id + task.position
   - Reorder: update position of all cards in affected columns
   - Optimistic UI: move card immediately, revert on error
   - Debounce position updates (batch saves)

6. Activity feed auto-generation:
   - PostgreSQL triggers on project_tasks, project_members, project_documents
   - Triggers insert into project_activity with metadata JSONB
   - This means activity is recorded even for direct DB changes
   - Comments are user-initiated (INSERT via app)

7. Migration numbering: 0085–0094 (general range)

8. T-code assignments:
   PJ01 — ProjectDashboard
   PJ02 — ProjectList (project cards/grid)
   PJ03 — ProjectDetail (board + tabs workspace)
   PJ04 — ProjectTasks (my tasks, cross-project)
   PJ05 — ProjectTimeline (Gantt)
   PJ06 — ProjectResources (cross-project allocation)
   PJ07 — ProjectReports
   PJ08 — ProjectAnalytics
   PJ09 — ProjectSettings

9. Key UX patterns:
   - Opening a project = opening a workspace (full-width, immersive)
   - Board is the default tab (most-used view)
   - Card modals overlay the board (don't navigate away)
   - Activity feed is always accessible (like Slack sidebar)
   - Costs tab pulls live data — no manual sync needed
   - Search works across tasks, comments, and documents

10. Performance considerations:
    - Board: load only active column cards (lazy-load archived)
    - Activity feed: paginate (load 50, infinite scroll)
    - Documents: thumbnail generation on upload (Supabase Edge Function)
    - Cost summary: server-side RPC (don't aggregate client-side)
    - Task count/stats: denormalized on project row via trigger
