1. Executive Summary

Bravura Resources is building a complete Enterprise Resource Planning platform to manage every business operation across multiple company sites — mines, processing plants, workshops, fuel stations, warehouses, and offices. The ERP is not a rewrite of any prior system; it is an evolution. The previous ERP (bravura-erp, built for Kamativi Mine) is the foundation from which concepts, workflows, database patterns, and reusable logic will be adopted and generalised.

The current platform (bravura-campsite) already ships three live modules: Workforce (employee tracking), Campsite (room management), and Meals (catering management). Two new modules are now being added simultaneously: Human Resources Management (led by Tafara) and Fuel Management (led by Clement). Both modules must integrate completely from the first day of development.

The target quality bar is SAP S/4HANA, Microsoft Dynamics 365, Oracle Fusion, ERPNext, and Odoo — but built for the modern web, following Google Material Design 3 principles, with an AI-first user experience.

Every decision documented here prioritises: scalability (unlimited sites, unlimited growth), integration (no isolated modules), maintainability (clean code, no shortcuts), and security (enterprise-grade RBAC at every level).

3. Project Vision & ERP Philosophy

3.1 Vision Statement

Build a complete, integrated Enterprise Resource Planning platform for Bravura Resources that manages every business operation across all company sites. The platform should feel like software built in the AI era — intelligent, responsive, and designed to assist rather than overwhelm. The quality bar is set by SAP S/4HANA, Microsoft Dynamics 365, and Oracle Fusion Cloud.

3.2 Core Principles

  • One ERP, Not Many Apps. All modules share one database, one authentication system, one permission model, one notification engine, one audit trail, one search index.
  • Multi-Site From Day One. Every table, every query, every report, every dashboard is site-aware. No data leaks across sites.
  • No Shortcuts That Break Future Integration. Every architectural decision must be compatible with future modules: Finance, Payroll, Procurement, Inventory, Fleet, Projects, Safety, Analytics, IoT.
  • Permission-Driven Everything. No page, no button, no action operates without a permission check. No hardcoded role names.
  • Soft Deletes Only. Records are never deleted. They are terminated, archived, released, or inactivated.
  • AI-First. Every module should feel intelligent. Users are assisted, not overwhelmed.

7. Multi-Site Architecture

7.1 Site Hierarchy

Company (Bravura Resources)
  └── Site (e.g. Kamativi Mine)

        ├── Fuel Tanks / Pumps / Bowsers

7.2 Database Pattern

Every table that holds site-scoped data includes site_id UUID NOT NULL REFERENCES sites(id). Row Level Security policies ensure users only access rows belonging to their site(s). Super-admins have a global role that bypasses site scoping for reporting purposes.

Table Typesite_id?Examples
Master dataYesemployees, fuel_tanks, vehicles, rooms
TransactionsYesfuel_transactions, leave_requests, meal_entries
Reference / lookupNo (shared globally)leave_types, fuel_types, currencies
System / authNoprofiles, roles, permissions, audit_logs
SettingsYes (site-specific config)module_settings

7.3 Cross-Site Features

  • Inter-site transfers — employees, fuel bowsers, stock between sites
  • HQ reporting — super-admins run reports across all sites
  • Consolidated dashboards — fleet-level KPIs aggregated from all sites
  • Shared lookups — fuel types, leave types, designations are global but can be overridden per site

8. Authentication & Authorization Design

8.1 Authentication Flow

  1. All authentication handled by Supabase Auth (JWT)
  2. Users log in with email + password
  3. Session persisted in localStorage; refreshed automatically by Supabase client
  4. On login, profiles row fetched to determine role, site(s), and permission overrides
  5. Session context available via AuthContext

8.2 Employee Account Creation Flow

  1. Toggle "Create System Account" on the employee form (optional — not all employees need access)
  2. On save, Edge Function calls supabase.auth.admin.inviteUserByEmail(email)
  3. Supabase sends invitation email with secure link
  4. Employee sets their own password on first login
  5. force_password_reset flag on profiles enforces password change
  6. profiles row auto-created by Supabase trigger; linked to employees.id
Employee accounts are OPTIONAL. Many employees (e.g. mine workers) will never log into the ERP. Their records still exist for reporting and fuel issuance tracking.

8.3 Password Policy

  • Minimum 10 characters, mixed case, 1 number, 1 special character
  • Temporary passwords expire after 72 hours
  • Force reset on first login (profiles.force_password_reset)
  • Password reset via Supabase magic link

9. Permission System — Granular RBAC

9.1 Permission Hierarchy

ERP Level           → super_admin: full access everywhere
  ↓
Module Level        → can access HR? can access Fuel?
  ↓
Feature Level       → within HR: can access Leave? can access Payroll?
  ↓
Page Level          → can VIEW the Employees page?
  ↓
Action Level        → can CREATE? can EDIT? can DELETE? can EXPORT?
  ↓
Button Level        → can click "Approve"? can click "Issue Fuel"?
  ↓
Workflow Level      → can initiate approval workflow? can be an approver?
  ↓
Report Level        → can view Payroll Report? can export Fuel Report?
  ↓
API Level           → enforced at database level via RLS
  ↓
Field Level         → can see salary fields? can see medical records?

9.2 Database Schema

roles(id, name, description, is_system)

permissions(id, code, module, action, description)
  -- e.g. code='hr.approve_leave', module='hr', action='approve_leave'

role_permission_grants(role_id, permission_id)

user_roles(user_id, role_id, site_id)
  -- site_id NULL = global role

user_permission_overrides(user_id, permission_id, granted BOOLEAN, site_id)
  -- grant or deny a specific permission for one user

9.5 usePermissions Hook Pattern

// hooks/usePermissions.js
export function usePermissions() {
  const { profile } = useAuth()
  const { currentSiteId } = useSite()

  const can = useCallback((code) => {
    if (profile?.role === 'super_admin') return true
    // Check user_permission_overrides first (most specific)
    // Then check role_permission_grants for all user roles
    return checkPermission(profile, code, currentSiteId)
  }, [profile, currentSiteId])

  return { can, role: profile?.role }
}

13. Dashboard Philosophy

Every module has its own dashboard. The dashboard answers one question: "What does this user need to know right now?"

Dashboards contain only: KPIs, Charts, Recent Activity, Pending Approvals, Alerts, Quick Actions, Upcoming Events. No clutter. No duplicate information. No unnecessary tables.

18. API Design Standards

  • All reads: supabase.from('table').select('*').eq('site_id', currentSiteId)
  • Always check for .error after every call
  • Use .select('*, relation(id,name)') for FK joins
  • Default sort: .order('created_at', { ascending: false })
  • Paginate all list queries with .range(from, to)
  • Never bypass RLS from client — sensitive operations go through Edge Functions with service role

19. Development Standards & Coding Conventions

Standard Page Component

import { useState, useEffect } from 'react'
import { THEME, MODULE_COLORS } from '../../utils/permissions'
import { Card, Icon, PageHeader, TableWrap, THead, Th, TRow, Td } from '../../components/ui'
import { useSite } from '../../contexts/SiteContext'
import { usePermissions } from '../../hooks/usePermissions'

export default function PageName() {
  const { currentSiteId } = useSite()
  const { can } = usePermissions()
  const [data, setData] = useState(null)
  const [loading, setLoading] = useState(true)

  if (!can('module.view')) return <AccessDenied />

  useEffect(() => {
    if (!currentSiteId) return
    async function load() {
      const { supabase } = await import('../../supabaseClient')
      const { data, error } = await supabase
        .from('table')
        .select('*')
        .eq('site_id', currentSiteId)
        .eq('is_archived', false)
        .order('created_at', { ascending: false })
      if (error) { console.error(error); return }
      setData(data)
      setLoading(false)
    }
    load()
  }, [currentSiteId])

  if (loading) return <LoadingSpinner />
  return ( ... )
}

What Never To Do

  • Never hardcode role names in permission checks
  • Never delete rows from the database
  • Never assume a single site — always scope to site_id
  • Never store money as FLOAT
  • Never bypass RLS from the client
  • Never write to profiles.meals_pin
  • Never use CSS files — inline styles only
  • Never skip the site_id filter on any query
  • Never reference the 'approver' role anywhere
