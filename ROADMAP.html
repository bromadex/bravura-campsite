SECTION 1

Executive Summary

Bravura ERP is a multi-site management platform serving mining and camp operations across Zimbabwe. The current platform (bravura-campsite) already handles Campsite Management, Meal Management, and basic Workforce tracking. This roadmap defines the expansion into two new full-scale modules: HR Management and Fuel Management, while preserving and deepening the existing architecture.

Multi-Site is Non-Negotiable. Every feature in both modules must be designed for N sites from day one. No single-site assumptions, no global queries without a site_id filter, no hardcoded site names. All data, reports, permissions, and workflows are scoped to site_id, and super-admins can switch between sites at any time.

Current System State

The following is already live and deployed on main:

ModuleStatusKey Features Live
Campsite Management✓ LiveRoom assignments, blocks, headcount, occupancy reports, supplies (with stock transfers), floor plan
Meal Management✓ LiveDaily entry, kitchen confirmation, approvals, flags, billing, pricing, reports (daily/range/monthly), meal providers
Workforce (Basic)✓ LiveEmployee list, contractor list, leave management, workforce reports (site-scoped)
Administration✓ LiveUser management, audit log viewer, data-driven RBAC via can('module.action')
HR Management (Full)⚒ BuildingEmployee accounts, documents, onboarding, performance — this roadmap
Fuel Management⚒ BuildingFuel tanks, vehicles, dispensing, deliveries, transfers — this roadmap

Guiding Principles

  • Site-first data model — every table has site_id; every query filters by it.
  • Data-driven RBAC — never hardcode role names in UI; always use can('module.action') from usePermissions().
  • No deletion, only archiving — employees are terminated, fuel records are voided, never deleted.
  • Audit trail on everything — all sensitive mutations go to audit_logs with actor, timestamp, before/after.
  • Email-first account delivery — credentials delivered only by email; no plaintext passwords in the UI.
  • Progressive disclosure — start with the most important features; add complexity phase by phase.
  • Integration before isolation — before coding any feature, map every table it touches across ALL modules.
SECTION 2

Architecture & Multi-Site Design

Site Switching

The SiteContext (already live) exposes currentSiteId and currentSite to every component. Every Supabase query in both new modules must include .eq('site_id', currentSiteId) unless it is explicitly a cross-site admin view.

Rule: Any developer who writes a query without a site_id filter must add a comment explaining why. Cross-site queries are only permitted in admin-level reports and must use RLS policies to enforce it server-side.

Row-Level Security (RLS) Strategy

All new tables must have RLS enabled. Policy templates:

-- Standard site-scoped read policy
CREATE POLICY "site_read" ON fuel_tanks
  FOR SELECT USING (
    site_id IN (SELECT site_id FROM user_site_access WHERE user_id = auth.uid())
  );

-- Write requires explicit permission grant
CREATE POLICY "site_write" ON fuel_dispensing
  FOR INSERT WITH CHECK (
    site_id = (current_setting('request.jwt.claims', true)::json->>'site_id')
  );

Cross-Site Features (Admin Only)

  • Fleet-wide fuel dashboard — total consumption across all sites, ranked by site.
  • HR headcount summary — total employees per site, per contractor, across the group.
  • Inter-site stock & fuel transfers — initiated at site A, accepted at site B.
  • Employee transfers — HR action that changes employees.site_id and creates a movement record.

SECTION 3

Granular Permission System

The current system uses can('module.action') with broad actions like employees.view. The new modules require per-page, per-button granularity: the same user can view a fuel dispensing list but not create a new record, or can read HR documents but not delete them.

Permission Levels

LevelWhat it controlsExample
VIEWWhether the nav item / page is visible at allCan the user see "Fuel Dispensing" in the sidebar?
READWhether data loads and is displayedCan the user see the list of fuel records? Individual record detail?
WRITECreate and edit operationsCan the user add a new dispensing record or edit an existing one?
DELETEArchive/void/terminate operationsCan the user void a fuel record or terminate an employee?
APPROVEWorkflow approval actionsCan the user approve a fuel request or a leave application?
EXPORTPrint/download/report accessCan the user export the fuel consumption report to PDF?

New Permission Data Model

-- Replaces / extends the current roles table
CREATE TABLE role_permission_grants (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  role_id uuid REFERENCES roles(id),
  resource text NOT NULL, -- e.g. 'fuel.dispensing', 'hr.documents'
  action text NOT NULL, -- 'view'|'read'|'write'|'delete'|'approve'|'export'
  granted boolean NOT NULL DEFAULT false,
  site_id uuid REFERENCES sites(id), -- null = all sites
  UNIQUE(role_id, resource, action, site_id)
);

-- Per-user overrides (override role defaults for specific users)
CREATE TABLE user_permission_overrides (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid REFERENCES auth.users(id),
  resource text NOT NULL,
  action text NOT NULL,
  granted boolean NOT NULL, -- can grant OR revoke
  site_id uuid REFERENCES sites(id),
  granted_by uuid REFERENCES auth.users(id),
  created_at timestamptz DEFAULT now()
);

UI Hook: can(resource, action)

The existing usePermissions() context will be extended to load both role grants and user overrides, resolved server-side into a flat permission map cached in React context. Components use it identically to today:

// In any component
const { can } = usePermissions()

// Page visibility (nav)
can('fuel.dispensing', 'view')

// Button visibility
can('fuel.dispensing', 'write') // show Add button
can('fuel.dispensing', 'delete') // show Void button
can('fuel.dispensing', 'approve')// show Approve button
can('hr.documents', 'read') // load document list
can('hr.accounts', 'write') // show Create Account button

SECTION 4 — MODULE 1

HR Management Module

The HR Management module expands the current basic workforce tracking into a full employee lifecycle system. It is the backbone that other modules (Fuel, Meals, Campsite) rely on for employee data.

Adoption from Legacy ERP (bravura-erp): Features from the Kamativi-specific ERP will be generalised for multi-site use. Key adoptions: employee document vault, leave request workflow with line-manager approval, performance review forms, and payroll preparation exports.
1

Foundation — Employee Accounts & Granular Permissions

Weeks 1–3 · Tafara (primary), Clement (permissions integration)
FOUNDATION

1.1 — Employee Account Creation (Optional)

  • Per-employee flag: employees.has_account boolean DEFAULT false. Creating an account is an explicit HR action, never automatic.
  • Account creation flow: HR clicks "Create Account" on an employee record → enters email address → system calls supabase.auth.admin.inviteUserByEmail() → Supabase sends a magic-link / temp-password email automatically.
  • Initial password: Supabase generates a secure temporary password. On first login, the user is forced to change it via a password_change_required flag in their profile.
  • Email delivery: Supabase Auth handles all credential emails. No plaintext passwords are ever shown in the UI.
  • Account states: Invited (email sent, not yet logged in) → Active → Suspended → Disabled. HR can suspend or disable without deleting.
  • Linking: employees.auth_user_id uuid REFERENCES auth.users(id) links the employee record to their Supabase Auth account.
  • Role assignment: After account creation, HR assigns a role from the role list. The role determines base permissions; user-level overrides can be added per resource.

1.2 — New Granular Permission System

  • Implement role_permission_grants and user_permission_overrides tables (schema in Section 3).
  • Extend usePermissions() to resolve can(resource, action) from the database, not from hardcoded role lists.
  • Seed default permission grants for all existing roles (System Admin, Camp Supervisor, HR Officer, Meal Officer, Kitchen Staff) against all existing resources.
  • Build a Permission Manager UI page (Admin module) where an admin can toggle individual grants per role per resource per action — a full matrix grid with checkboxes.
  • Every new page in HR and Fuel must register its resource keys in a central PERMISSION_RESOURCES manifest so the Permission Manager auto-discovers them.

1.3 — Site-Scoped Account Access

  • A user account can have access to one or multiple sites. Table: user_site_access(user_id, site_id, role_id).
  • When a user logs in, their site access list is loaded into SiteContext — the site switcher only shows sites they have access to.
  • System Admins automatically get access to all sites.

Database Changes in Phase 1

  • Add auth_user_id, has_account, account_status, work_email to employees.
  • Create role_permission_grants, user_permission_overrides, user_site_access.
  • Create new roles: hr_manager, hr_officer, fuel_manager, fuel_operator.
  • Migrate existing profiles.role data into user_site_access.

Integration Impact (check before coding)

  • usePermissions() change affects EVERY page in the app — must be backward-compatible during migration.
  • Fuel module (Clement) must wait for the new can(resource, action) API to be merged before gating Fuel pages.
  • employees.auth_user_id is referenced by Fuel module for "who dispensed fuel" linking.

Core HR Features

Weeks 4–7 · Tafara (primary)
CORE

2.1 — Enhanced Employee Profiles

  • Personal details: Full name, ID number, date of birth, gender, nationality, marital status, physical address.
  • Emergency contacts: Name, relationship, phone — at least 2 required.
  • Employment details: Job title, department, employment type (permanent/contract/casual), start date, contract end date, probation end date, notice period.
  • Banking: Bank name, account number, branch code — for payroll export (not for actual payroll processing).
  • Skills & qualifications: Free-form tags for skills, certifications with expiry dates.
  • Profile photo — uploaded to Supabase Storage, displayed in employee list and profile page.

2.2 — Document Vault

  • Categories: National ID, Passport, Employment Contract, Medical Certificate, Driving License, Mine Safety Certificate, Training Certificate, Disciplinary Letter, Other.
  • Upload to Supabase Storage under employee-docs/{employee_id}/{doc_type}/.
  • Expiry tracking — documents with expiry dates show a warning badge 30 days before expiry.
  • Access control: hr.documents.read required to view; hr.documents.write to upload; hr.documents.delete to archive.
  • Employees with their own account can view their own documents under "My Documents" — gated by hr.documents.read.self.

2.3 — Leave Management (Enhanced)

  • Extend existing leave system with: leave balance tracking per category, leave request workflow (employee requests → supervisor approves → HR finalises).
  • Leave balances: Accrual rules per category (e.g. Annual: 2.5 days/month), carried-over balance, used balance, remaining balance.
  • Leave calendar: Site-level calendar showing who is on leave each day — blocks that could affect operations are highlighted.
  • Leave request: Employees with accounts submit leave requests through the portal; supervisors are notified (in-app notification + email if configured).
  • Approval chain: Line manager → HR Officer → auto-approved if no response within N days (configurable).
  • Clash detection: System warns if leave request overlaps with another team member's approved leave (configurable per team size threshold).

2.4 — Onboarding Checklist

  • When a new employee is added, an onboarding checklist is auto-generated: collect ID, sign contract, issue PPE, complete induction, create system account, assign room.
  • HR tracks completion of each step. Incomplete onboarding shows a warning on the employee record.
  • Checklist templates are configurable per site and per employment type.
  • Integration: "Assign room" step links directly to Campsite → Room Assignments. Completing that step marks the checklist item done.

2.5 — Offboarding / Termination Workflow

  • HR initiates termination → system generates offboarding checklist: return PPE, clearance from finance, room release, system account suspension, final leave balance calculation.
  • Integration: Termination automatically suspends the linked Supabase Auth account, releases any active room assignment, clears active fuel access.
  • Never delete — employee record is set to status = 'terminated', all history preserved.

SECTION 5 — MODULE 2

Fuel Management Module

The Fuel Management module tracks every litre of diesel/petrol that enters and leaves each site — from delivery receipt to vehicle dispensing. It integrates with HR (employee-linked dispensing), Finance (cost reporting), and the Camp module (generator fuel as a supply category).

Adoption from Legacy ERP: The Kamativi-site ERP had a vehicle log and basic fuel dispensing register. We generalise this for N sites, add multi-fuel-type support, inter-site transfer capability, and approval workflows for large fuel requests.
1

Infrastructure — Tanks, Vehicles & Fuel Types

Weeks 1–3 · Clement (primary)
FOUNDATION

1.1 — Fuel Types

  • Types: Diesel, Petrol, Paraffin, Aviation (extensible). Managed in a fuel_types lookup table.
  • Each tank holds one fuel type. Dispensing records reference the fuel type.

1.2 — Tank / Storage Management (Per Site)

  • Each site has one or more tanks: tank name, fuel type, capacity (litres), current level, location description, status (active/maintenance/decommissioned).
  • Tank level is derived: starting level + deliveries − dispensed = current level. Never stored as a single editable number (audit trail).
  • Low-stock alert threshold configurable per tank (e.g. warn when below 20%).
  • Integration: Camp Supplies module has a "fuel" category for generator fuel — Phase 1 must decide whether generator fuel routes through Fuel module or stays in Supplies. Decision: generator fuel goes through Fuel module, linked to a dedicated "Generator" vehicle record. Supplies module is updated to remove its fuel category.

1.3 — Vehicle & Equipment Registry (Per Site)

  • Vehicles: registration number, make/model, year, type (light vehicle, heavy equipment, generator, water pump, compressor, other), assigned site, ownership (Bravura / contractor), assigned contractor (if contractor-owned), current driver/operator (links to employees).
  • Equipment: asset tag, description, type, site, fuel type used, average consumption rate (litres/hour).
  • Status: active, grounded (maintenance), decommissioned — never deleted.
  • Integration with HR: vehicles.primary_driver_id → employees.id. The vehicle record is updated when an employee is terminated.

1.4 — Supplier Management

  • Fuel suppliers: name, contact person, phone, email, typical lead time, contracted price per litre per fuel type.
  • Supplier records are global (not site-scoped) since the same supplier can deliver to multiple sites.

Database Changes in Phase 1

CREATE TABLE fuel_types (id, name, unit text DEFAULT 'litres');
CREATE TABLE fuel_tanks (id, site_id, name, fuel_type_id, capacity_litres, low_alert_threshold, status);
CREATE TABLE vehicles (id, site_id, registration, make, model, type, ownership, contractor_id, primary_driver_id, fuel_type_id, status);
CREATE TABLE fuel_suppliers (id, name, contact_name, phone, email);

Core Fuel Operations

Weeks 4–7 · Clement (primary)
CORE

2.1 — Fuel Deliveries (Receipts)

  • Record incoming fuel delivery: date, supplier, tank, litres received, price per litre, total cost, delivery note number, received by (employee), notes.
  • On save: tank level increases by delivered litres. An audit_logs entry is written.
  • Attachments: photo of delivery note / GRN uploadable to Supabase Storage.
  • Deliveries can be edited within 24 hours (write permission required); after that, corrections must use a Void + Re-enter workflow.

2.2 — Fuel Requests

  • Any user with fuel.requests.write can raise a fuel request: vehicle/equipment, fuel type, quantity requested, purpose, requested date.
  • Approval workflow: Request → Pending → Approved / Rejected. Users with fuel.requests.approve see a pending queue.
  • Approved requests generate a "fuel chit" — a reference number that the fuel operator uses when recording actual dispensing.
  • Requests with quantity above a configurable threshold (e.g. 500 litres) require dual approval.

2.3 — Fuel Dispensing

  • Operator records dispensing: date/time, tank, vehicle/equipment, fuel chit reference (optional — can dispense without pre-request for small operational top-ups), odometer/hours reading, litres dispensed, dispensed by (operator employee), driver/operator (employee).
  • On save: tank level decreases. If this would take the tank below the low-alert threshold, a warning is shown (but not blocked — operator can override).
  • Validation: Cannot dispense more than tank current level. Cannot dispense to a vehicle that is grounded. Cannot dispense to a driver whose driving license is expired (warning, not hard block — operator must acknowledge).
  • Integration with HR: Driver employee ID looked up; certification check runs against employee_training_records.

2.4 — Inter-Site Fuel Transfers

  • Site A initiates transfer: from tank, to site, to tank (at destination), litres, reason, date.
  • Status: Pending → In Transit → Received / Rejected.
  • Site A's tank level decreases on initiation. Site B's tank level increases on receipt confirmation.
  • Requires fuel.transfers.approve at both sites.
  • Transfer record preserved on both sites' audit trails.

Reporting & Cost Control

Weeks 8–10 · Clement (primary), Tafara (cross-module reports)
ADVANCED

3.1 — Fuel Consumption Reports

  • By vehicle: litres consumed per period, cost, km/litres or litres/hour efficiency trend.
  • By department/contractor: total fuel consumed by contractor employees, cost allocation.
  • By tank: running balance chart, delivery vs. dispensing over time.
  • By fuel type: totals across all tanks at a site.
  • All reports are site-scoped; cross-site summary available to System Admin.
  • Print-ready (uses existing print-only CSS) and CSV export.

3.2 — Cost Reporting & Budget Tracking

  • Total fuel cost per month per site, variance against budget (if budget is set).
  • Cost per vehicle — identify high-consumption or inefficient vehicles.
  • Price trend chart — cost per litre over time per supplier.
  • Finance role can see cost data; operators cannot (gated by fuel.costs.read).

3.3 — Anomaly & Leakage Detection

  • Tank reconciliation: (opening balance + deliveries) − dispensed = expected closing balance. Variance flags potential leakage or meter inaccuracy.
  • Unusual consumption alert: if a vehicle's litres/km ratio spikes >30% above its 30-day average, flag it for review.
  • Orphan dispensing: dispensing records without a fuel chit above a configurable threshold are flagged.

3.4 — Fuel Module Dashboard

  • Site dashboard: tank levels (visual gauge), today's dispensing total, pending requests, recent deliveries, low-stock alerts.
  • Quick actions: New Dispensing, New Delivery, New Request — gated by respective permissions.

Automation & Fleet Intelligence

SCALE

4.1 — Automated Reorder Alerts

  • When a tank drops below its reorder threshold, a fuel request is auto-drafted and the Fuel Manager is notified.

4.2 — Vehicle Service Integration

4.4 — Mobile-Friendly Dispensing Entry

  • Fuel operators in the field often use phones. The dispensing entry form must be fully usable on mobile — large inputs, minimal scrolling, offline-capable (queue locally, sync when connected).

-- DB function: derived tank level
CREATE OR REPLACE FUNCTION get_tank_current_level(p_tank_id uuid)
RETURNS numeric AS $$ SELECT
  COALESCE((SELECT SUM(litres_received) FROM fuel_deliveries WHERE tank_id=p_tank_id AND NOT voided), 0) -
  COALESCE((SELECT SUM(litres_dispensed) FROM fuel_dispensing WHERE tank_id=p_tank_id AND NOT voided), 0) +
  COALESCE((SELECT SUM(litres) FROM fuel_transfers WHERE to_tank_id=p_tank_id AND status='received'), 0) -
  COALESCE((SELECT SUM(litres) FROM fuel_transfers WHERE from_tank_id=p_tank_id AND status!='rejected'), 0)
$$ LANGUAGE SQL STABLE;

Before Writing Any New Page — Checklist

  1. Identify every table the page reads from or writes to.
  2. For each table: who owns it? Does it need a new column? Does the RLS policy allow this user's access pattern?
  3. Identify every other page or module that reads the same table — will this change break them?
  4. Map the permission resource key: module.page.action — is it in the permissions manifest?
  5. Does this page need to fire a notification? Add it to the notification type list.
  6. Does this page need an audit log entry? Add it to the audit event list.
  7. Is the page printable? Add print-only header and no-print controls.
  8. Is the page correctly filtering by currentSiteId for all queries?
